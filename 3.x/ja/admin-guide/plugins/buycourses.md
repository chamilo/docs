# BuyCourses: 支払いと定期サービス

**BuyCourses** プラグインは、コースおよびセッションへのアクセスを販売し、有料サービスを提供できます。利用できる支払い方法は、インストール環境に設定されているゲートウェイによって異なります。

## 支払い設定

**Administration > Plugins > BuyCourses** を開き、支払い設定の領域に移動します。ゲートウェイの認証情報は、学習者向けページではなくサーバー上で管理してください。Stripe や PayPal などの既存の方法は、BTCPay Server とは独立して動作し続けます。

### BTCPay Server（コースおよびセッションの購入）

このプラグインは、コースおよびセッションの購入に **BTCPay Server** も対応しています。

1. BuyCourses の設定で BTCPay の支払い方法を有効にします。
2. BTCPay の **Server URL**、**Store ID**、**Greenfield API key**、および **webhook secret** を設定します。
3. 支払い設定の **connection test** を使用して、Greenfield API へのアクセスを確認します。
4. プラグインに表示される webhook URL と同じ secret を使用して、BTCPay 側で webhook を設定します。
5. 学習者にこの選択肢を提供する前に、少額のテスト購入を完了します。

購入者は BTCPay がホストするチェックアウトにリダイレクトされます。Chamilo は webhook の署名を検証し、請求書を再度取得して、注文を支払い済みとしてマークし購入者を登録する前に、**store、amount、currency、および order details** を検証します。ブラウザーからの復帰により、欠落または遅延した webhook を照合できます。通知が繰り返されても、履行が重複して作成されることはありません。

検証済みの決済済み支払い（承認された過払い、および管理者が明示的に決済済みとマークした請求書を含む）のみがアクセスを付与します。**部分的、遅延、期限切れ、または無効な支払いを、自動的に履行済みとして扱ってはなりません**。例外的な支払いには手動での確認が必要です。

**既存のインストール:** プラグインの更新手順を一度実行し、`plugin_buycourses_btcpay_account` を作成します。管理者は `/plugin/BuyCourses/update.php` を開くか、BTCPay の支払い設定を保存できます。これにより、プラグインのテーブルが存在することも保証されます。この更新は BuyCourses 固有のものであり、グローバルなデータベース移行ではありません。

BTCPay は、ここでは定期サービスのゲートウェイとしては**文書化されていません**。Stripe/PayPal 形式の自動サブスクリプション更新を実装していると想定しないでください。

## 定期サービスのライフサイクル

学習者は **My Services** を使用して、有効な定期サービスと購入／支払い履歴を確認できます。自動更新に対応しているサービスについては、次のとおりです。

* 各更新支払いには、独自の履歴レコードと領収書があります。
* 更新をキャンセルすると、今後の請求は行われなくなりますが、支払い済みのサービスは現在の支払い期間が終了するまで利用できます。
* 管理者は **service sales report** から更新をキャンセルすることもできます。
* 有効、保留中、またはその他の状態で継続中の定期サブスクリプションは、重複購入から保護されます。
* 期限切れ、または完全にキャンセルされたサービスは、再度購入できます。

**Purchase history** と **payment history** は別です。1 件のサービス購入に、複数の更新支払いが含まれる場合があります。更新された支払いを 2 回目の購入であると推測しないでください。

## サービス販売の支払い合計

管理者の **service sales report** では、当初の注文金額と、時間の経過とともに回収された支払いを区別するのに役立つ 2 つの列があります。

* **Last payment** は、そのサービス販売について記録された直近の成功した支払いの日付を表示します。支払い日が利用できない場合、レポートにはダッシュが表示されます。
* **Total collected** は、最初に回収された購入金額に、記録された成功した更新金額を加えたものを、サービスの通貨で整形して表示します。これは、単一の請求期間の価格と同じではありません。

この計算はサービス販売の監査履歴を使用し、重複する更新イベントを計上しないようにし、最初の Stripe サブスクリプション請求を二重に計上せずに考慮します。例外的な支払いまたは返金の場合は、レポートを決済プロバイダーと照合してください。表示される金額は、ゲートウェイの支払額や、別の返金台帳ではありません。

## 過去の Stripe サブスクリプション

BuyCourses は、更新トランザクションがプラグインの監査ログに完全には記録されていない、古い定期サービスについて、Stripe の請求書履歴を照合できます。**My Services** ビューとサービス販売レポートは、それらのレコードを更新し、ローカルに把握している支払い済み期間と合計を更新できます。管理者は、販売を直接編集するのではなく、例外的な支払い履歴の差異を Stripe と照合して確認する必要があります。

## 販売レポートのフィルタリング

**course and session sales report** は、注文ステータス、ユーザー、日付範囲、またはメールでフィルタリングできます。任意の製品フィルターにより、製品タイプと製品名で結果を絞り込むことができます。**service sales report** は、ステータスによるフィルタリングに加え、ユーザー／メール／名前／注文参照の検索と、サービス名の検索に対応しています。エクスポートまたは販売の照合を行う前に、有効なフィルターを確認してください。2 つのレポート画面では、フィルターの操作が異なります。

[BuyCourses sales filters PR #9387](https://github.com/chamilo/chamilo-lms/pull/9387) を参照してください。

## サブスクリプション連動のコースライフサイクルと削除の保護措置

BuyCourses は、定期サービスサブスクリプションに関連付けられたコースを、支払い状況の変化に応じて終了、非表示、再有効化できます。サービスの **Subscription behavior JSON** では、`hide_after_days` が終了後にコースを非表示にするまでの遅延（既定は 30 日）を指定し、`delete_after_days` が非表示後に完全削除するまでの遅延を指定します。削除は既定で無効（`null`）であり、正の値を設定した場合にのみコースが削除対象になります。

管理者は、対象、保留中、およびブロックされたコースを `/admin/buycourses/course-lifecycle` で確認できます。この画面では、非破壊的なシミュレーションと、明示的な確認を伴う **1 回の実行につき対象コース 1 件** の削除を行えます。CLI プロセッサ `chamilo:buycourses:process-recurring-subscriptions` も `--dry-run`、`--delete-expired`、`--max-deletions`（1–25）をサポートします。`--delete-expired` を指定しない場合、コースは完全には削除されません。

**完全削除は破壊的です。** バックアップを保持し、まず使い捨て用のコースでテストしてください。適格性チェックは、販売中のコース、セッションに関連付けられたコース、および所有関係の不整合を保護します。複数のアクセス URL を持つインストールでは、自動削除はブロックされます。本番環境で破壊的なクリーンアップをスケジュールする前に、更新と削除が同時に発生する動作を確認してください。[subscription course lifecycle PR #9442](https://github.com/chamilo/chamilo-lms/pull/9442) を参照してください。

## 運用上の確認

アップグレード後は、コース購入の一連の流れ、販売している場合はセッション購入、遅延または再送された webhook、期限切れおよび一部支払いの BTCPay 請求書、自動更新、ならびに支払い期間の終了までアクセスが継続する解約をテストしてください。認証情報と webhook のシークレットは、スクリーンショット、ログ、サポートチケットに含めないでください。

## 決済の強化

### ゲートウェイ金額の照合（Redsys / Cecabank）

銀行がプラットフォームに支払い成功を通知したとき、BuyCourses は銀行が請求した金額（署名付き通知のセント単位）と販売価格を比較します。両者が異なる場合、通知は拒否され、販売は保留のままとなり、PHP エラーログに `[BuyCourses] Redsys notification refused` または `[BuyCourses] Cecabank notification refused` の行が書き込まれます。通常の支払いは影響を受けません。

購入者が支払ったにもかかわらず販売が保留のままの場合は、ログを確認してください。注文作成後に価格が変更された場合、または一部支払いの場合は、そこに記録されます。確認後、販売レポートから当該販売を手動で完了してください。

### セキュリティトークン

* クーポンフォーム（追加 / 設定）、公開プランカードフォーム、および支払いアクションは、他のすべてのプラグイン管理ページと同じ BuyCourses 管理トークンを使用します。長時間開いたままのフォームでも、セッションが有効である限り動作します。ログアウトして再度ログインした後は、保存する前にページを再読み込みしてください（そうしないと "Not validated" メッセージが表示されます）。
* 「請求書を依頼」ページ（`request_invoice.php`）と `process_recurring_subscriptions.php` の Web トリガーには、リンク内のトークン（`buycourses_admin_sec_token=...`）が必要です。トークンなしでブックマークまたはメール送信されたリンクは "Not validated" を表示します。コマンドライン / cron の実行（`php .../process_recurring_subscriptions.php` またはコンソールコマンド）は変更されておらず、トークンは不要です。
* 成功ページ（PayPal、Stripe、サブスクリプション、サービス）は、購入したユーザーにのみ販売内容を表示します。
* 支払いアクション（PayPal 一括支払い、支払いのキャンセル）はプラットフォーム管理者に制限され（セッション管理者は受け付けられなくなりました）、トークン付きの POST として送信する必要があります。

### 日付

サブスクリプション販売の終了日は、販売日と同様に、サーバーのタイムゾーンにかかわらず常に UTC で計算されるようになりました。

### 複数 URL の制限

サービスの期限切れ時に適用されるコース作成およびホスティングの制限は、プラットフォームの他の部分と同じ規則に従います。メイン URL でロックされている、または変更不可とマークされている設定は、別の URL から上書きできません。
