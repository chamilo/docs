# OAuth 2.1 認可サーバーと MCP クライアント

Chamilo は、保護されたリソースに接続するクライアント向けの **OAuth 認可サーバー** として動作できます。これは、Chamilo が外部のアイデンティティプロバイダーを使用してユーザーをサインインさせる [OAuth2 ログイン](oauth2.md) とは異なる機能です。

## 有効化と設定

**管理 > 設定 > セキュリティ** で、`security.oauth_server_enabled` を有効にします。MCP アクセスは、既存の `security.mcp_enabled` 設定と、ユーザーに許可された MCP ロールにも依存します。

サーバーは、標準の認可、トークン、登録、失効のルート（`/oauth/authorize`、`/oauth/token`、`/oauth/register`、`/oauth/revoke`）とディスカバリメタデータを公開します。本番クライアントでは HTTPS のみを使用してください。

## クライアントの登録

Chamilo は、公開 PKCE 認可コードクライアントと、登録済みの機密クライアントをサポートします。動的クライアント登録（DCR）は `/oauth/register` を使用し、レート制限が適用されます。`security.dynamic_client_registration` 設定は **デフォルトで無効** です。エンドポイントはサポートされている MCP 登録フローでは引き続き利用できますが、この設定は登録時に受け入れられる追加のクライアントスコープを制御します。この設定を切り替えるだけで、任意の保護された API が利用可能になるとは考えないでください。

登録済みクライアントには、サーバー側の **許可リソース** リストがあります。現在、リソースレジストリが定義しているのは **MCP** リソースと `mcp` スコープのみです。新しい保護リソースには、リクエストに未認識の URL を追加するだけでは不十分であり、明示的なサーバー実装と権限の判断が必要です。Chamilo は、認可およびトークン処理の全体を通じて RFC 8707 の `resource` パラメータを検証します。

## ユーザーの同意と監査

1. クライアントは、PKCE（`S256`）と要求されたスコープ／リソースを含む認可コードリクエストを開始します。
2. 必要に応じて、ユーザーは通常の Chamilo ログインで認証します。
3. Chamilo は同意画面に、クライアントの識別情報、登録の詳細、および要求されているアクセスを表示します。
4. ユーザーは **許可** または **拒否** を選択します。承認はサーバーの同意履歴の一部として記録され、以前の承認情報が後続のリクエストで表示される場合があります。

同意は、ユーザーに表示されたリクエストに紐づけられます。承認されたリクエストは、要求された権限を超えて他の保護リソースや任意のアクセスを付与するものではありません。

## デプロイとセキュリティに関する注意

OAuth 2.1 の更新では、クライアント向けの許可リソースフィールドと、永続的なクライアント同意レコードが導入されます。更新されたフローを有効にする前に、リリースに同梱されている **Chamilo 固有のデータベースマイグレーション** を適用してください。コールバック URL と OAuth クライアントシークレットは非公開にしてください。クライアント登録によって、Chamilo のユーザーやコースへの無制限のアクセスが付与されるわけではありません。

実装の参照: [OAuth クライアント登録と同意、PR #9231](https://github.com/chamilo/chamilo-lms/pull/9231)。
